# アプリ開発開始時のコメント禁止と再発防止

コメント検査・追加ルールの実行・導入処理の編集元は `repo-preflight`。アプリへ生成した検査は配布物として扱い、共通部分の修正はこの正本へ戻す。この手順は独立したアプリのリポジトリにも適用する。対象リポジトリの既存の検査・言語・共同開発の契約を確認してから接続する。

## 実装前に検査を通す

1. 既存の静的検査と継続検査を確認する。説明コメント・説明専用の文書文字列を禁止する検査と、再発防止ルールを実行する入口が揃っていれば再利用する。
2. 足りない場合は、利用可能な `repo-preflight` のローカル導入入口を使う。新規リポジトリ作成のスキルも、この正本が生成する同じ検査を同梱する。既存ファイルに競合があれば差分を確認し、利用中の検査へ統合してから再実行する。
3. 下の導入・実行コマンドを対象リポジトリで使う。`<skill-dir>` は実行環境で利用可能なスキルの場所に置き換える。

```bash
python3 <repo-preflight>/scripts/install_development_lint.py --repo <repo> --json
python3 -m pip install -r tools/development-lint-requirements.txt
python3 tools/development_lint.py
```

生成した検査の `JavaScript`・`TypeScript` 用解析器は `Python 3.10` 以降を使う。依存の導入は対象の仮想環境で行う。既存の依存管理手段がある場合は、同じ固定依存をその手段で解決する。生成した `tools/lint_rules/README.md` の対象言語を確認する。検査対象は `git ls-files` で得る追跡済みと無視されていない未追跡ファイルであり、無視設定も確認する。対象アプリの言語が未対応なら、その言語の既存の構文解析器を使った検査を接続する。未対応の言語を検査済みとは扱わない。

4. 作業用の小さなファイルで、説明コメントは失敗し、文字列中のコメント記号は成功することを確認する。ライセンス・実行・型検査などに必要な記述は、許可条件と消費するツールを確認する。既存コードへの導入時は、残る説明を命名・構造・テスト・設計文書へ移す。
5. 同じコマンドを継続検査で実行する。既存のワークフローがあればその入口に接続し、二重実行を避ける。リポジトリの管理者が要求する検査設定と、設定変更に必要な権限は別途確認する。

## バグを直すたびに検査を育てる

- 問題を再現し、型や構造で同じ誤りを書けなくできるか確認する。
- コード上のパターンで判定できる問題は、既存の静的検査ルールを有効化・拡張する。既存ルールで表せない場合は、対象を絞った検査を `tools/lint_rules/` に加え、共通コマンドから実行する。追加規約は同じディレクトリの説明を読む。
- 元の違反例を拒否し、似た正常例を許可するテストを追加する。診断には問題の場所と修正方法を含める。誤検出が起きた入力もテストに残す。
- 結果や操作順序に依存する問題は、実装の振る舞いを確かめる回帰テストにする。既存の状態遷移検証があれば対応も更新する。
- バグ修正の差分には、選んだ防止手段、違反例と正常例の結果、共通コマンドの実行結果を含める。判断が必要で機械検査に落とせない部分は、その理由を既存のレビュー記録へ残す。

## 適用範囲を確認する

初期設定の検査は手順の入口であり、以後のバグごとのルール作成は修正担当の責務。対象範囲の除外、例外、検査器の変更も通常のコードレビューで確認する。配置した検査、ローカルで実行した検査、遠隔の継続検査で実行された結果を分けて報告する。
