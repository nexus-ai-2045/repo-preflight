停止条件集。個別の指摘を 1 件ずつ直すのではなく、「次に同じ型を書かない」ために使う。

**この file は生成物。手で編集しない。** 正本は private repository 側にあり、
そこには型ごとの実例・件数・出典 PR が入っている。ここに出しているのは、
どのリポジトリでも同じように使える停止条件だけ。

公開・外部送信・承認の境界そのものは、作業中のリポジトリの安全境界文書
(`AGENTS.md` など) が正本。この file は境界を定義しない。

## R1 検査は未確定を合格にしない

取得失敗・空・未知・タイムアウト・例外を、正常な `pass` と同じ経路へ落としている。
検査を足したのに、その検査が最も必要な場面で黙って通る。

停止条件:

- 結果は 2 値 (`ok`/`ng`) ではなく 3 値以上 (`ok` / `blocked` / `unknown`) を持つ。
- 「読めなかった」「0 件だった」「例外だった」を `ok` に合流させない。
- 検査を追加したら、対象を壊した状態で必ず落ちることを 1 回確認する。
- 終了コードは意味ごとに分ける。整合性失敗と未保護状態を同じコードに畳まない。

## R2 明示指定は黙って別の対象へ倒れない

停止条件:

- 優先順位は「明示引数 > 環境変数 > 既定」。明示指定が無効なら fallback せずエラー終了。
- 既定値は実行環境から導出する。個人のホームパスやマシン固有パスを埋め込まない。
- fallback したときは、どこへ倒れたかを必ず出力する。

## R3 証拠を対象に結び付ける

「検査した」「承認された」という記録が、何を対象にした結果なのか分からない。
検査後に対象が変わっても、古い合格がそのまま生きる。

停止条件:

- 検査結果は `(対象 ID, revision または content hash, 実施時刻)` と一体で記録する。
- 検査から実行 (merge / push / 公開) までの間に対象が変わり得るなら、実行直前に再検証する。
- 記録する時刻は「実際に観測した時刻」。予定時刻や未来時刻を書かない。
- 承認は操作単位で結び付ける。汎用の「レビュー済み」を別操作へ流用しない。

## R4 宣言と実体を一致させる

停止条件:

- 文書が「ここにある」と書いたパスは、同じ commit の tree に存在させる。
  追跡しない生成物を指すなら「ここにある」と書かず、生成コマンドを書く (R13)。
- 未実施のチェック項目は未チェックのまま残す。予定を完了として書かない。
- 手順に書いたコマンドは、書いた通りの cwd で実際に走らせて確認する。
- 追跡できない一次資料は、取得元・ハッシュ・復元手順を残す。

## R5 正本と配布コピーを同時に更新する

停止条件:

- 更新は「正本 → 配布」の一方向。配布側だけを直さない。
- 手順のコマンドは、配布物自身の位置 (`__dirname` / skill ディレクトリ) から解決する。
- 追跡から外した生成物は、生成に必要な依存とソースを追跡側に残す。

## R6 実行環境差を前提に置く

停止条件:

- 依存は宣言する。標準ライブラリのみを維持するなら、その制約で動く経路を用意する。
- 相対パスの基準を対象ごとに分ける。絶対パスを埋め込まない。
  - CLI 引数で明示された相対パス → 実行時の cwd。スクリプト位置を基準にしない (R2)。
  - 設定ファイル内の相対パス → その設定ファイルの位置。
  - 同梱リソースと内部の既定値 → スクリプト位置。
- テストは HOME・グローバル git config・インストール済みコピーから隔離する。
- OS 専用の処理は、対象外プラットフォームで skip するかエラーにする。黙って誤判定しない。

## R7 入力は型・範囲・重複・サイズまで検証する

停止条件:

- 集合参照・比較・スライスの前に型を確認する。
- 空・null・重複・負数・境界値を、そのフォーマットの表記ゆれ込みで正規化してから判定する。
- サイズ・時間・件数の上限は、読み込みながら適用する。
- 例外を投げるのではなく構造化エラーを返す。エラーにも入力そのものを載せない (R8)。

## R8 秘密情報と個人情報は出力経路すべてで落とす

「保存前に落とす」実装はあるが、エラーメッセージ・ログ・レポート・コミット本文が
出力経路として抜けている。

停止条件:

- 出力経路は「表示・ログ・レポート・コミット・PR 本文・外部送信」すべて。片方だけ塞がない。
- redaction を入れたら、既存データの移行も同じ変更に含める。
- secret パターンは、対象プロバイダの現行フォーマットを実際に 1 つ試して確認する。

## R9 部分失敗を成功にしない

停止条件:

- 多段書き込みは stage → swap。live な配置先は swap 成功まで残す。
- 途中失敗したら、それまでに変更した分を戻すか、戻せない残骸を明示して失敗終了する。
- 「一部成功」を戻り値と終了コードで表現できるようにする。

## R10 文字列マッチに境界を持たせる

停止条件:

- 語の判定はトークン境界で行う。部分一致で分岐しない。
- Markdown / YAML / JSON は構文として解析する。行頭一致や正規表現で近似しない。
- 日本語と ASCII が連結する箇所は、ASCII 側の終端を明示する。

## R11 承認・公開境界で実際に破られた経路

境界の定義そのものはそのリポジトリの安全境界文書 (`AGENTS.md` など)が正本。ここには「まだ外に出ていない」と
誤認して漏れた経路だけを書く。

レビューで実際に指摘された抜け道:

- private repository への初回 push。private でも外部送信。
- draft release の作成と、その後続 PR の作成。
- PR とその PR コメントの作成。
- 共有済み Drive フォルダの更新。可視範囲と対象内容の提示が要る。
- 承認の粒度。汎用の「レビュー済み」で個別操作を通さない。
- 承認の鮮度。現在の会話での承認を要求する。
- 承認と対象の結合。承認を packet の内容そのものに紐付ける。

停止条件:

- 上の経路に触れる操作をする前に、そのリポジトリの安全境界文書 (`AGENTS.md` など) の該当節を読み、そこに書かれた
  条件だけに従う。この文書は承認条件を定義しない。
- 上の経路が `AGENTS.md` の現行文から読み取れない場合は、`AGENTS.md` 側を更新する。
  ここに別の条件を書き足して二重化しない。

## R12 CI ゲート自身を守る

停止条件:

- ゲートは base / 既定ブランチ側の実装で評価する。head の変更で実装を差し替えさせない。
- ゲート自身の実装や定義を変更する PR では、base 側の検査だけで通さない。
  base 側の信頼済みゲートで差分と権限を検査したうえで、**head 側の新しいゲートも実行して
  テストする**。head 側の実行は、secret と書き込み権限を渡さない隔離環境で行う。
  これをしないと、旧ゲートが通した壊れた新ゲートが merge 後に有効になり、
  次の PR から保護が消える。
- 承認と検査結果は `(base SHA, head SHA)` の組、または実際に検査した merge-group SHA に
  結び付ける。どちらかが変わったら失効させて再検査する。head SHA だけに結び付けると、
  承認後に base が進んだ場合に head が同じまま merge されるツリーだけが未検査の組み合わせへ
  変わり、ゲートを迂回できる。
- merge は、検査したその組み合わせに固定して実行する。
- ゲート自身の定義ファイルの変更を、免除対象にしない。

## R13 追跡の取捨は「作り直せるか」で決める

停止条件:

- ignore パターンは、生成物の具体名か出力ディレクトリに限定する。拡張子の一括除外をしない。
- 追跡が必須なのは、一次資料と再生成できない素材。文書から参照されているだけでは理由にならない。
- 参照先が再生成できるなら追跡しなくてよい。ただし R5 のとおり、生成に必要なソース、依存、
  復元手順を追跡側に残す。復元できないなら、それは再生成可能ではない。
- private データの除外は、実際に ignore が効いていることを確認してから記録する。

## R14 指摘は型で再発する

同一タイトルの完全一致は 2,068 件中 7 件しかない。一方で「同じ型が別の場所で再発」は多い。
個別修正で閉じても再発が止まっていない。

停止条件:

- 指摘を直したら、同じ型を機械で捕まえる検査へ昇格させる。修正だけで閉じない。
  機械判定を作れない指摘 (承認文言の明確さ、文書の事実性など) は例外にできる。その場合は
  機械化できない理由と、代わりに行った手動確認を PR に記録する。無記録で閉じない。
- 修正 PR には、その型が再発していないことの確認を含める。
- レビューコメントが 0 件のときは、レビューが実施されたかどうかを先に確認する。
  確認する項目は次の 3 つ。
  1. PR が draft でないか。
  2. レビュー基盤が上限やエラーで停止していないか。
  3. **レビュー済み SHA が現在の head と一致しているか**。ずれていれば、
     `@codex review` のように再検査を実際に発火させる明示要求を出してから判断する。
- レビューを受ける段階になったら draft を外す。draft のまま完了扱いにしない。
- P1 は merge をブロックする。P2/P3 は carryover 台帳へ載せ、完了まで消さない。

## PR 前セルフレビュー

差分に対して上から順に確認する。該当なしなら飛ばす。

1. 追加した検査は、対象を壊した状態で実際に落ちるか (R1)。
2. 取得失敗・空・例外を `ok` と別の状態で返しているか (R1)。
3. 明示引数が無効なとき、fallback せずエラーにしているか (R2)。
4. 既定値に個人パス・マシン固有パス・cwd 依存が残っていないか (R2, R6)。
5. 「検査した」記録に、対象 ID と revision と実測時刻が入っているか (R3)。
6. 検査から実行までの間に対象が変わり得るなら、直前に再検証しているか (R3)。
7. 文書・台帳・manifest が指す参照先を確認したか (R4, R13)。
   一次資料と再生成できない参照先は、この commit の tree に存在するか。
   再生成できる参照先は、ソース・依存・復元手順が追跡されているか。
8. 手順のコマンドを、書いた cwd で実際に 1 回走らせたか (R4)。
9. 正本と配布コピーの両方を更新したか。新しい依存を宣言したか (R5)。
10. Windows / macOS / Linux / CI のどれで壊れるかを 1 回考えたか (R6)。
11. テストが HOME・グローバル git config・インストール済みコピーに依存していないか (R6)。
12. 集合参照・比較の前に型検査があるか。重複・負数・空・上限を見ているか (R7)。
13. エラーメッセージとログに、入力値・credential・絶対パスが載っていないか (R8)。
14. 多段書き込みが stage → swap になっているか。途中失敗を戻せるか (R9)。
15. 語の判定がトークン境界か。Markdown/YAML を構文として解析しているか (R10)。
16. 外へ出る操作 (push / PR / release / Drive / 投稿) をする前に、`AGENTS.md` の該当節を読み、
    そこに書かれた条件を満たしたか (R11)。条件はこの文書では判断しない。
17. CI ゲートを base 側実装で評価し、承認を `(base SHA, head SHA)` に結び付けて
    どちらかの変更で失効させているか。ゲート自身を変更したなら、secret と書き込み権限を
    渡さない隔離環境で head 側の新ゲートも実行したか (R12)。
18. ignore パターンが一次資料まで巻き込んでいないか (R13)。
19. 過去に同じ型の指摘を受けたコードか。検査へ昇格させたか (R14)。
20. レビューを受ける段階なら draft を外したか。レビュー済み SHA は現在の head と一致するか。
    ずれていれば再検査を明示要求したか。指摘 0 件を未検査と取り違えていないか (R14)。

## 指摘の閉じ方

1. 指摘の**型**を R1〜R14 のどれかに割り当てる。当てはまらなければ、この文書に型を追加する。
2. 修正する。同時に、同じ型を機械で捕まえる検査を足せるか判断する。
3. 足せるなら足す。足せないなら、なぜ足せないかを PR に書く。
4. P1 は merge 前に閉じる。P2/P3 は carryover 台帳へ載せ、閉じるまで消さない。
5. レビューコメント 0 件のときは、レビューが実施されたことを確認してから完了扱いにする。
